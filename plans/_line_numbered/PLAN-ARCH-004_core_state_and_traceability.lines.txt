L000007 | ## PLAN-ARCH-004:SEC-01 Purpose and bounded outcomes
L000008 | 
L000009 | This plan establishes the first executable canonical-state slice for Project Pipeline. It defines stable domain identities, strict requirement entities, a domain project manifest, explicit project and task lifecycle state, production and local persistence boundaries, reversible migrations, transactional requirement traceability, query and mutation services, CLI access, validation, tests, and evidence.
L000010 | 
L000011 | The bounded result must:
L000012 | 
L000013 | - retain the validated JSON/JSONL registries as source authority during migration;
L000014 | - compile those registries into typed, queryable persistent state;
L000015 | - keep deterministic authority outside language-model memory;
L000016 | - make project and task transitions explicit, versioned, and auditable;
L000017 | - support bidirectional source/plan/Jira/code/test/evidence traversal;
L000018 | - fail closed on invalid identifiers, transitions, schema input, or stale revisions;
L000019 | - provide a production PostgreSQL schema behind replaceable repository ports;
L000020 | - provide an executable SQLite local profile with equivalent semantic entities;
L000021 | - create no external Project Pipeline mutation.
L000022 | 
L000023 | ## PLAN-ARCH-004:SEC-02 Stable domain identities
L000024 | 
L000025 | Project, requirement, Jira, plan, plan-section, acceptance, evidence, decision, and migration identifiers retain their established human-readable forms. Content-derived operational identifiers use SHA-256 over canonical semantic parts and a type-specific prefix:
L000026 | 
L000027 | - `TRACE-` for normalized traceability links;
L000028 | - `TRANS-` for immutable state transitions;
L000029 | - `IMPORT-` for catalog imports;
L000030 | - `MUT-` for traceability mutation audit records.
L000031 | 
L000032 | Identifiers are validated by semantic kind. An unknown or ambiguous identifier is rejected. Repeating the same semantic operation produces the same digest identifier, allowing deterministic reconciliation without conflating different entity types.
L000033 | 
L000034 | ## PLAN-ARCH-004:SEC-03 Typed requirements and project manifest
L000035 | 
L000036 | Every row in `plans/_traceability/requirements.jsonl` is represented by strict `RequirementRecord` validation. Exact source ranges, plan and section identities, Jira identities, decisions, implementation paths, tests, evidence, dispositions, and implementation states remain explicit. Completed requirement states require implementation, test, and evidence links.
L000037 | 
L000038 | `config/project_manifest.json` is the domain manifest for the controlled project. It is distinct from the root file-integrity manifest. The domain manifest records:
L000039 | 
L000040 | - project identity and revision;
L000041 | - project origin and runtime profile;
L000042 | - exactly one primary repository;
L000043 | - authoritative source, requirement, plan, Jira, and evidence locations;
L000044 | - semantic fingerprint and UTC lifecycle timestamps.
L000045 | 
L000046 | An unchanged manifest rebuild is byte-stable and does not increment the revision.
L000047 | 
L000048 | ## PLAN-ARCH-004:SEC-04 Project and task state model
L000049 | 
L000050 | Project and task lifecycle state is deterministic. Each state record carries an optimistic version, updated timestamp, and the last immutable transition identity. Task state additionally carries priority, dependencies, blockers, owner, and bounded block reason.
L000051 | 
L000052 | Allowed transitions are explicit tables. A transition requires:
L000053 | 
L000054 | - entity type and identity;
L000055 | - previous and next state;
L000056 | - expected and resulting versions;
L000057 | - actor identity;
L000058 | - correlation identity;
L000059 | - bounded reason;
L000060 | - UTC occurrence time.
L000061 | 
L000062 | Invalid transitions, no-op transitions, stale versions, and malformed blocked-state metadata fail before persistent state changes.
L000063 | 
L000064 | ## PLAN-ARCH-004:SEC-05 Persistence ports and authority boundaries
L000065 | 
L000066 | PostgreSQL remains the selected production transactional authority behind internal repository ports. The production schema stores project manifests, project state, task state, immutable transitions, requirements, normalized links, catalog imports, and mutation audit records.
L000067 | 
L000068 | SQLite is the deterministic local execution profile. It uses the same domain entities, migration identifiers, state-transition rules, revision semantics, and traceability behavior. Local runtime state defaults beneath `.local/` and is excluded from permanent manifests and archives.
L000069 | 
L000070 | During this stage:
L000071 | 
L000072 | - validated JSON/JSONL registries remain source authority;
L000073 | - the database is an executable projection and transactional work surface;
L000074 | - proposed changes may be exported for review;
L000075 | - the database never silently overwrites authoritative repository catalogs;
L000076 | - no live PostgreSQL verification is claimed without a configured server and credentials.
L000077 | 
L000078 | ## PLAN-ARCH-004:SEC-06 Migration lifecycle and rollback
L000079 | 
L000080 | `database/MIGRATION_CATALOG.json` is the migration authority. Each ordered migration records dependencies, compatibility phase, reversibility, dialect-specific paths, and SHA-256 digests.
L000081 | 
L000082 | Migration execution must provide:
L000083 | 
L000084 | - contiguous deterministic order;
L000085 | - dependency closure;
L000086 | - one atomic transaction per migration;
L000087 | - idempotent reapplication;
L000088 | - reverse-order rollback;
L000089 | - no applied record after a failed transaction;
L000090 | - digest validation against committed SQL;
L000091 | - SQLite behavioral verification;
L000092 | - PostgreSQL DDL parity without unverified live-runtime claims.
L000093 | 
L000094 | Production activation additionally requires pre-migration backup, restore readiness, compatibility verification, controlled application, and post-migration evidence.
L000095 | 
L000096 | ## PLAN-ARCH-004:SEC-07 Transactional traceability service
L000097 | 
L000098 | The traceability service imports the strict requirement catalog transactionally and normalizes every relationship into a typed link. It supports:
L000099 | 
L000100 | - requirement-to-source, plan, section, Jira, implementation, test, evidence, decision, open-decision, and evolution traversal;
L000101 | - source-to-requirement traversal;
L000102 | - arbitrary target-to-requirement traversal by link type;
L000103 | - catalog digest and import identity;
L000104 | - persisted-versus-authoritative equivalence verification;
L000105 | - deterministic projection export.
L000106 | 
L000107 | A traceability mutation includes requirement ID, add/remove operation, link type, target, expected revision, actor, correlation ID, and reason. Changed mutations increment the requirement revision exactly once. Semantic no-ops preserve the revision. Stale revisions fail closed. All accepted attempts receive immutable audit records and `PROPOSED_CHANGE` authority.
L000108 | 
L000109 | ## PLAN-ARCH-004:SEC-08 CLI and operator inspection
L000110 | 
L000111 | The CLI exposes bounded local operations:
L000112 | 
L000113 | - `state init` compiles the domain manifest, project state, Jira task state, and requirement traceability into the local store;
L000114 | - `state status|project|task|migrations` provides machine-readable inspection;
L000115 | - `state transition-project|transition-task` applies version-checked state changes;
L000116 | - `trace-store init|status|requirement|source|target` provides bidirectional traceability inspection;
L000117 | - `trace-store add|remove` records proposed mutations with optimistic concurrency;
L000118 | - `trace-store export` writes a reviewable projection without replacing source authority.
L000119 | 
L000120 | The CLI rejects missing required parameters and rejects the local command surface when a PostgreSQL profile is selected but not live configured.

L000141 | ## PLAN-ARCH-004:SEC-10 Evidence, recovery, and remaining boundaries
L000142 | 
L000143 | Completion evidence records test output, migration validation, state snapshots, traceability equivalence, CLI results, repository validation, and clean-archive verification with hashes.
L000144 | 
L000145 | Local recovery consists of closing the store, preserving or deleting the `.local` database as appropriate, recreating it from the committed migration catalog, and reimporting the authoritative registries. Migration rollback is dialect-specific and reverse ordered.
L000146 | 
L000147 | This bounded implementation does not claim the complete Project Control Kernel, live PostgreSQL operation, durable workflow activation, remote Jira/GitHub synchronization, scheduling, provider routing, Command Center APIs, Windows packaging, or AWS deployment. Those remain governed by later component plans and verification gates.
