L000007 | ## PLAN-LIFE-002:SEC-01 Purpose and engineering outcomes
L000008 | 
L000009 | The repository engineering foundation turns the accepted architecture into an installable, typed, self-validating Python package without introducing premature services. It establishes one practical source layout, one configuration authority, explicit dependency states, versioned contracts, correlation-aware telemetry, deterministic bootstrap commands, and local quality gates.
L000010 | 
L000011 | Required outcomes are:
L000012 | 
L000013 | - imports resolve from the `src/` package rather than the repository root;
L000014 | - active dependencies have exact locally verified versions and provenance evidence;
L000015 | - unavailable resolver or tool access remains explicit rather than being replaced by fabricated artifacts;
L000016 | - configuration rejects unknown fields and never stores secret values;
L000017 | - command, event, transition, diagnostic, and adapter-error payloads are versioned and machine-validatable;
L000018 | - local command execution demonstrates idempotency and immutable artifact integrity;
L000019 | - the CLI provides bounded diagnostics, configuration, schema, dependency, smoke, quality, and validation operations;
L000020 | - CI defines the same required checks that developers run locally;
L000021 | - all completed claims link to tests and evidence.
L000022 | 
L000023 | ## PLAN-LIFE-002:SEC-02 Practical source and package boundaries
L000024 | 
L000025 | The executable package remains a modular monolith under `src/project_pipeline/`. Subpackages own distinct semantics:
L000026 | 
L000027 | - `configuration` owns layered settings, profiles, secret references, and configuration schema validation;
L000028 | - `contracts` owns versioned Pydantic models and deterministic JSON Schema export;
L000029 | - `core` owns command processing, results, errors, and the local idempotency journal;
L000030 | - `observability` owns correlation context, structured logging, redaction, and the OpenTelemetry provider boundary;
L000031 | - `runtime` composes diagnostics and executable smoke verification;
L000032 | - existing architecture, requirement, Jira, evidence, artifact, upstream, and repository-validation modules remain authoritative for their established data.
L000033 | 
L000034 | Dependencies between these packages flow toward contracts and ports. No runtime package may import continuation/session-state materials, and external-provider semantics remain behind ports.
L000035 | 
L000036 | ## PLAN-LIFE-002:SEC-03 Dependency declaration, locking, and activation
L000037 | 
L000038 | `pyproject.toml` is the declaration authority. Dependency groups are separated by lifecycle:
L000039 | 
L000040 | - `runtime` and `group:test` are active and must be represented in the observed-environment lock;
L000041 | - API, database, OTLP, and quality groups remain declared but activation-gated until their dependencies and operational prerequisites can be resolved and verified;
L000042 | - dependency source incorporation remains a separate decision from package activation.
L000043 | 
L000044 | The active lock records exact versions, applicable dependency closure, and SHA-256 hashes of installed distribution metadata. Deterministic pin exports are generated from that lock. A cross-platform resolver-produced `uv.lock` remains required before release; if package-index metadata is unavailable, the resolver state is `BLOCKED_EXTERNAL` with an activation command and verification method. Handwritten resolver output is prohibited.
L000045 | 
L000046 | Every dependency addition requires:
L000047 | 
L000048 | 1. a capability rationale;
L000049 | 2. a removal boundary;
L000050 | 3. license and provenance review;
L000051 | 4. activation state;
L000052 | 5. compatibility and regression tests;
L000053 | 6. rollback instructions.
L000054 | 
L000055 | ## PLAN-LIFE-002:SEC-04 Typed configuration and secret references
L000056 | 
L000057 | Configuration precedence is deterministic:
L000058 | 
L000059 | 1. committed base configuration;
L000060 | 2. selected committed profile;
L000061 | 3. optional explicit JSON configuration;
L000062 | 4. `.env` and process environment values;
L000063 | 5. explicit CLI overrides.
L000064 | 
L000065 | Pydantic models use `extra=forbid`, immutable instances, and validated defaults. Paths remain relative to the project root unless intentionally absolute. External writes default to denied or dry-run behavior and require explicit approval authority.
L000066 | 
L000067 | Secret-bearing settings accept references only. Supported reference forms are `env://NAME` and repository-confined `file://relative/path`. Secret resolution is demand-driven, never included in configuration fingerprints, and never emitted to logs or generated configuration artifacts.
L000068 | 
L000069 | ## PLAN-LIFE-002:SEC-05 Versioned contracts and generated schemas
L000070 | 
L000071 | The contract boundary includes:
L000072 | 
L000073 | - action intent;
L000074 | - command envelope and result;
L000075 | - state transition;
L000076 | - event envelope;
L000077 | - adapter error payload;
L000078 | - diagnostic snapshot;
L000079 | - runtime configuration;
L000080 | - secret reference.
L000081 | 
L000082 | Contracts reject unknown fields, use timezone-aware UTC timestamps, carry correlation and idempotency identities, and encode error/retry/unknown-outcome semantics. Generated JSON Schemas use Draft 2020-12, stable filenames, schema identifiers, and deterministic formatting. Repository validation fails when a committed schema differs from its authoritative model.
L000083 | 
L000084 | ## PLAN-LIFE-002:SEC-06 Structured logging and telemetry foundation
L000085 | 
L000086 | Correlation context carries project, workflow, task, run, actor, correlation, and causation identifiers. Structured JSON logging merges this context with trace identifiers and event attributes. Configured sensitive-field markers and secret types are redacted recursively; byte values are summarized instead of emitted.
L000087 | 
L000088 | OpenTelemetry is the portable tracing boundary. A local provider can be created without a remote exporter. OTLP export is profile-gated and cannot be enabled without an endpoint. Telemetry failure is observational and cannot become deterministic workflow authority.
L000089 | 
L000090 | ## PLAN-LIFE-002:SEC-07 Bootstrap and executable core slice
L000091 | 
L000092 | Bootstrap diagnostics verify:
L000093 | 
L000094 | - supported Python version;
L000095 | - repository root availability;
L000096 | - active runtime dependencies;
L000097 | - runtime-path writability or preparability;
L000098 | - safe external-write defaults;
L000099 | - telemetry state;
L000100 | - optional quality-tool availability;
L000101 | - repository contract when requested.
L000102 | 
L000103 | The executable core slice submits a typed command through a registered handler, writes an atomic idempotency journal record, emits a typed transition and event, replays the same semantic command without calling the handler again, stores evidence bytes in the content-addressed artifact store, and verifies their digest. Different semantics under the same idempotency key fail closed.
L000104 | 
L000105 | ## PLAN-LIFE-002:SEC-08 Quality gates and CI
L000106 | 
L000107 | Required local and CI checks are:
L000108 | 
L000109 | - Python compilation;
L000110 | - behavioral tests;
L000111 | - branch-aware coverage threshold;
L000112 | - generated-schema validation;
L000113 | - dependency-state validation;
L000114 | - repository self-validation;
L000115 | - Ruff lint and format verification;
L000116 | - strict Mypy verification for the new executable packages;
L000117 | - package build;
L000118 | - runtime dependency vulnerability audit.
L000119 | 
L000120 | Local environments may report optional tools unavailable when strict mode is not requested. CI treats configured quality tools as required. CI uses read-only repository permissions, bounded timeouts, matrix Python versions, and preserves audit evidence when available.
L000121 | 
L000122 | ## PLAN-LIFE-002:SEC-09 Developer setup and operating commands
L000123 | 
L000124 | Portable and PowerShell bootstrap scripts set `PYTHONPATH`, prepare runtime paths, validate active dependency state and generated schemas, and run tests. They perform no external Project Pipeline integration mutation.
L000125 | 
L000126 | Primary commands are:
L000127 | 
L000128 | - `project-pipeline doctor` for bounded prerequisite inspection;
L000129 | - `project-pipeline config validate` for effective configuration and fingerprinting;
L000130 | - `project-pipeline bootstrap --prepare` for local runtime preparation;
L000131 | - `project-pipeline smoke` for the executable foundation journey;
L000132 | - `project-pipeline dependencies lock|validate|status|snapshot` for dependency evidence;
L000133 | - `project-pipeline schemas write|check` for contract schemas;
L000134 | - `project-pipeline quality` for local quality orchestration;
L000135 | - `project-pipeline validate` for repository-wide self-audit.
L000136 | 
L000137 | ## PLAN-LIFE-002:SEC-10 Verification, evidence, and rollback
L000138 | 
L000139 | Completion requires behavioral tests for configuration precedence, secret confinement, contract invariants, redaction, context restoration, idempotent replay, semantic-key conflict, runtime preparation, smoke integrity, dependency lock determinism, and CLI behavior.
L000140 | 
L000141 | Evidence records must contain command output or generated validation artifacts and their hashes. Runtime state under `.local/` is excluded from the permanent repository and removed before manifest generation and packaging.
L000142 | 
L000143 | Rollback consists of reverting the package/configuration changes, restoring the prior manifest, and removing generated runtime state. Dependency activation can be rolled back independently because optional integrations and quality tools do not own deterministic domain semantics.
L000144 | 
L000145 | ## PLAN-LIFE-002:SEC-11 Remaining boundaries
L000146 | 
L000147 | This foundation does not claim completion of persistent PostgreSQL state, durable workflow activation, scheduler semantics, remote Jira/GitHub writes, Command Center services, Windows packaging, AWS deployment, or remote telemetry export. Those capabilities remain governed by their dedicated plans and acceptance gates.
